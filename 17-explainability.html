Module 17 · Part IV — Shipping it

Explaining a model's predictions

Sooner or later someone in a design review points at a prediction and asks “why?”. This module is the practical toolkit for answering that about tabular and engineering models: what the standard methods compute, how to read them, and the specific ways they mislead people who trust them too much.

The claim this module defends

Every method here explains the model, not the physics. Used that way — to find bugs, leakage and nonsense before a model ships — they are among the most useful tools in the subject. Used as evidence that the model has learned how brakes work, they will eventually embarrass you. Every lab below is trained and computed live in your browser on synthetic data whose true equations we know, so you can see exactly where each explanation is right and where it is not. Module 14.3 covered the research on looking inside language models; this one is for the models you are more likely to put into a product.

17.1 · Two different questions

“Explain the model” is two requests that people run together. The tools for each are different, and so are the mistakes.

Global

“What has this model learned, across all the data?”

Which inputs matter overall, and what shape the relationship has. This is the question a design review asks of a model before it is trusted.

Tools: permutation importance (17.3), partial dependence (17.4), or a model simple enough to read directly (17.2).

Local

“Why did it say this for this case?”

Which inputs pushed one prediction up or down, and by how much. This is the question asked when a single part is rejected or a single forecast looks wrong.

Tools: individual conditional expectation curves (17.4), Shapley values (17.5).

One dataset runs through most of the module. It is synthetic and the equations below were written for teaching: they have a plausible shape, and they are not calibrated to any real brake system. The point of using invented data is that we know the true answer, so we can mark each explanation method's homework.

// AUTHORED — the data-generating process for one track session (n = 900, seeded) pressure ~ uniform 25–85 bar ambient ~ uniform 5–38 °C duct ~ uniform 0–100 % open laps ~ integer 5–30 compound = road or track, 50/50 severity ~ normal(0, 1) // circuit braking severity, not recorded disc temp = 330 + 3.4·pressure − 1.5·duct + 2.5·ambient + 40·severity + noise wear (mm) = laps × 0.03 × (0.5 + pressure/60) × g(disc temp, compound) × noise g = road: exp((T − 500)/150) track: 0.75·exp((T − 560)/220) + 0.6·max(0, (450 − T)/80) // track pads also suffer when cold

Read it once and remember three things: ambient temperature and duct opening affect wear only through disc temperature; the two pad compounds respond to heat differently (an interaction); and wear is proportional to laps. The model is a gradient-boosted tree ensemble — 200 trees of depth 3, the method from module 6.3 — trained on 600 sessions and tested on the other 300.

  • About 4 minutes. Put the generator on screen and leave it there for a moment — the whole module is “compare the explanation with what we know is true”, which you can never do on real data. Say that out loud.
  • Expect: “why synthetic, why not our data?” Because on real data you cannot tell whether an explanation is right. Run these methods on your own data afterwards, knowing how they fail.
  • Timing for the module: 17.1 four minutes, 17.2 six, 17.3–17.6 about seven each, 17.7 and 17.8 three each.

17.2 · Interpretable by construction, or explained afterwards

There are two routes. Build a model whose structure is the explanation, or build whatever predicts best and explain it afterwards with the methods in 17.3–17.5. The second route is more common. The first deserves to be tried first, more often than it is.

Linear and logistic models

The coefficient is the explanation: one more bar of pressure adds this many millimetres of wear. Exactly right if the relationship is linear; confidently wrong if it is not, and the model does not warn you.

Shallow trees and rule lists

Three or four levels of if-then rules can be printed on one page and checked by a domain expert line by line (module 6.2). Accuracy usually costs a little; reviewability is excellent.

Constrained models

Keep a flexible model and forbid shapes you know are physically wrong. Monotonic constraints — “wear may not fall as disc temperature rises” — are supported by XGBoost, LightGBM and CatBoost, cost one line of configuration, and are underused.

Test RMSE is measured on 400 fresh sessions from the same generator; a reversal is a place where predicted wear goes down as temperature goes up, counted on a 1 °C grid.

What the constraint buys

Usually almost no accuracy, sometimes a little more — and a property you can state in a review without a single plot: the model's wear prediction never decreases with disc temperature, for any input. That is a guarantee about the model, not a description of a test set, and it is the kind of sentence certification engineers like. Use constraints where the physics is not in doubt; do not use them to impose a belief you have not checked.

  • About 6 minutes. Start at 40 sessions and noise 0.3: the unconstrained curve has small backwards steps. Then drop to 15 sessions — the steps get worse. Then raise to 300 — they shrink but rarely vanish.
  • The straight line is there to make the point that “interpretable” is not the same as “right”: it has zero reversals and the worst error, because the truth is curved.
  • Expected question: “is a reversal always wrong?” No — some physics genuinely is non-monotonic (the track compound in 17.4 is). The constraint is a claim you make; make it only when you would defend it.

17.3 · Permutation importance: break a column, see what breaks

The most honest global importance measure is also the simplest. Take the test set, shuffle one column so it no longer lines up with the rest of the row, and measure how much worse the predictions get. A feature the model relies on hurts a lot when scrambled; one it ignores does not hurt at all. It works for any model, because it only needs predictions.

importance(feature) = error with that column shuffled − error on the real data Here the error is root-mean-square error in millimetres of wear, so importance is in millimetres too. Repeat with several shuffles and report the spread.

Measure it on held-out data

On the training set, importance measures what the model memorised. On the test set it measures what the model relies on and that generalises. Increase the depth and watch the two diverge. Importance on training data is a common and quiet error in reports.

Be wary of the built-in importance

The grey bars are the “feature importance” most libraries print by default: total split gain. On this clean synthetic data it broadly agrees with the permutation result — say so when you see it. In general it is computed on training data, so it cannot separate signal from memorisation, and it is known to favour features with many distinct values, such as IDs and timestamps. Where the two disagree, believe the permutation on held-out data.

  • About 7 minutes. Point out first that the ranking matches the generator: disc temperature, laps and compound at the top; duct and ambient near zero, because they act only through disc temperature, which the model can see directly.
  • Then depth 1: the model can no longer represent the compound × temperature interaction, test error rises, and compound's importance changes. Importance describes this model, not the problem.
  • Expected question: “a small negative importance?” Shuffling happened to help slightly by chance; read it as zero. That is why we repeat the shuffles and show the range.

17.4 · Partial dependence and ICE: the shape of a relationship

Importance tells you how much a feature matters; it does not tell you which way. For that, take one session, sweep one input across its range while holding the other inputs where they are, and plot the prediction. That curve is an ICE curve (individual conditional expectation). Do it for many sessions and average them: that average is the partial dependence curve.

Two traps in one picture

The average hides the cases. Partial dependence is one line; the population underneath may be two groups going in opposite directions. Always plot the ICE curves behind it.

The sweep invents sessions. Sweeping disc temperature to 680 °C on a session with the duct fully open and low pressure produces a combination that never occurred, and the model is extrapolating there. Partial dependence treats the features as if they were independent; when they are not, part of the curve is the model's guess about impossible conditions. Section 17.6 returns to this.

  • About 7 minutes. Disc temperature first, uncoloured: one rising curve. Tick the compound box and it splits into two families — road pads climb steeply, track pads climb slowly and rise again at the cold end. The partial dependence is the average of two behaviours that neither compound actually has.
  • Then laps: fan-shaped ICE curves, all rising, with very different slopes. Centring makes the fan obvious. That fan is the multiplicative structure in the generator.
  • Then duct: nearly flat. Hold that thought for 17.7 — it is the most important line in the module, and it is misleading.

17.5 · Shapley values: sharing out one prediction

For a single session the model predicts, say, 2 mm of wear, and the average session is about 0.8 mm. The question “why 1.2 mm more than average?” is a fair-division problem: six features co-operated to produce the difference, and we want to share it between them. Game theory answered this in 1953. The Shapley value of a feature is its marginal contribution averaged over every order in which the features could have been revealed to the model. It is the only way of sharing that satisfies a short list of fairness properties, one of which matters a lot in practice: the contributions add up exactly to the prediction minus the baseline.

φi = ΣS ⊆ others |S|! (p − |S| − 1)! / p! · [ v(S ∪ {i}) − v(S) ] v(S) is the model's average prediction when the features in S are fixed to this session's values and the rest are taken from a background set of real sessions. With p = 6 features there are 2⁶ = 64 coalitions, so this page computes every one of them: exact enumeration, no sampling and no approximation. The popular SHAP library uses faster algorithms that approximate this quantity, or compute it exactly for trees.

An explanation relative to something

Change the background and the explanation changes — sometimes the sign of a contribution flips. That is not a bug. A Shapley value answers “why is this session different from that group?”, and the group is a choice you must state. “Compared with all sessions in the 2025 test programme” is a complete explanation; a bare waterfall is not.

Additive, so it smears interactions

The model's compound × temperature interaction has to be credited to one feature or the other, and the Shapley rule splits it between them. Nothing in the chart tells you that an interaction exists. Read a waterfall as an accounting of one prediction, not as a description of mechanism.

  • About 7 minutes. Show the check figures first: Σφ matches f − E[f] to around 10⁻¹⁶. That is the property people rely on, and here it is computed rather than asserted.
  • Highest-wear session (road pads), background “all”: disc temperature and laps dominate. Switch to “road pads only”: the compound bar drops to exactly zero, because every reference session has road pads too, and the baseline moves up. Same model, same session, different question.
  • Expected question: “is this what the SHAP library does?” Same quantity (interventional Shapley values against a background set). The library avoids enumerating 2p coalitions, which matters at 50 features and does not at 6.
  • Model calls: 64 coalitions × background size. That is why background size is a cost knob, and why small backgrounds make noisier explanations.

17.6 · The correlated-features trap

A new dataset with the same physics and a twist that every real telemetry set has: two sensors measuring nearly the same thing. Disc temperature and pad temperature both respond to the same heat load; wear depends on that heat load, which neither sensor measures perfectly. Pressure and laps are also present. Importance gets shared out

With two near-copies, the model can use either. Each one, scrambled alone, barely hurts — the other covers for it. So the strongest physical driver in the data can rank below a weaker one simply because it was measured twice.

The split is arbitrary

Which twin gets the credit depends on details of the training run. A report that says “disc temperature is twice as important as pad temperature” may be describing the random seed. Retrain before you quote a ratio.

What to do instead

Shuffle correlated features as a group and report the group (the green bars, which are stable). Or drop one twin and retrain. Or measure the dependence first — a correlation matrix takes a minute and tells you which importances not to trust.

  • About 7 minutes. Start at 0.95. Point at the green bars: steady across retrains and above the laps line. Then the blue and orange: each well below laps, and the ratio between them moving around from one retrain to the next.
  • Then the scatter. Every red dot is a session with, say, a 650 °C disc and a 330 °C pad. No such session exists, the model has never seen one, and the importance number is partly a measurement of how the model behaves there. The same is true of partial dependence (17.4) and of Shapley values with an independent background (17.5).
  • Drag down to 0.3: the red cloud is no longer distinguishable from the real one, and the twins are no longer twins. The trap needs correlation, which real sensor data almost always has.

17.7 · An explanation is not a cause

Back to the brake data and to the flat line for duct opening in 17.4. The model is right: given disc temperature, the duct tells it nothing more, because in our generator the duct acts only by cooling the disc. Every explanation method above correctly reports that the model does not use the duct. An engineer who reads that as “the duct does not affect wear” has drawn the wrong conclusion from a correct chart: opening the duct is a strong lever.

The general rule

Explanation methods describe how the prediction depends on the inputs as the model sees them. Whether changing an input in the world changes the outcome is a causal question, and it depends on how the data came about — designed experiment or operating history — and on which variables were recorded. No amount of explanation tooling on observational data replaces a designed test. Module 7.6 covers causality properly — confounders, and why correlation is not a knob; module 11.2, on where to put the samples, is the constructive answer.

  • About 3 minutes, and possibly the most important three in the module. With randomised duct settings, model B (which cannot see disc temperature) recovers the true effect reasonably well, because randomisation removes confounding. That is exactly why designed experiments exist.
  • Switch to “set by engineers”: engineers open the duct at severe circuits, which run hotter. Model B now sees open ducts alongside high wear and reports little or no benefit — at low cooling effect, it says opening the duct increases wear. Every number on screen is an honest computation; the conclusion is still wrong.
  • Expected question: “so which model is right?” Both, about different questions. A is right about prediction; neither answers “what if we open the duct?” without the causal structure.

17.8 · What to put in front of a design review

Explanations are debugging tools. They are very good at finding a model that is right for the wrong reason — a leaked timestamp (module 7.4), a sensor ID standing in for a test rig, a relationship with the wrong sign. They are poor evidence that a model is right for the right reason, because each method has the blind spots this module has just demonstrated.

Bring

  • Permutation importance on held-out data, with the spread over shuffles and over retrains, and correlated features grouped.
  • Partial dependence with ICE curves behind it, restricted to the range where data exists, and a note of which features are correlated.
  • For every relationship whose direction the physics fixes, a check that the model agrees — or a monotonic constraint that makes it agree by construction.
  • A handful of local explanations for the worst errors and the most consequential predictions, each with its background set stated.
  • The things you found and fixed using these tools. That list is the most persuasive evidence that the tools were used seriously.

Do not claim

  • “The model has learned the physics.” It has learned a function that fits the data; the explanation is of that function.
  • “Feature X does not matter.” It does not matter to this model, given the other inputs — see 17.7.
  • “X is twice as important as Y” when X and Y are correlated — see 17.6.
  • Any explanation as a substitute for the validation evidence of module 8 and module 11.8. Accuracy on a representative, held-out test set is the evidence; the explanation is how you decide whether you believe it.
Key takeaway

Ask of every explanation: relative to what, on which data, and would it survive a retrain? Prefer models that are constrained or simple enough not to need much explaining, where you can afford to. Where you cannot, use the post-hoc tools as instruments for finding faults — and remember that for safety-relevant functions the argument rests on validation, bounded operating conditions and monitoring, which is where module 20 picks up.
