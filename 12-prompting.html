Module 12 · Part III — Applying it

Prompting

A workshop rather than a lecture. This is the skill that the largest number of people in your company will actually use, it takes about an hour to teach, and the difference between doing it badly and doing it well is roughly the difference between a novelty and a tool.

The frame that makes this click

Module 4 showed that the model predicts the most plausible continuation of the text in front of it. So a prompt is not a command — it is a description of the situation in which the answer you want would be the plausible thing to say. Everything below follows from that. You are not persuading the model; you are narrowing the space of plausible continuations.

12.3 · Six techniques, ranked by how much they pay

1 · Give the context it cannot have

The model does not know your company, your constraints, your reader or your standards. Almost every disappointing answer is a missing-context problem rather than a model problem.

Do: paste the relevant document, state who the reader is, say what has already been decided and what is out of scope. The most common improvement of all is simply pasting more of the actual material.

2 · Specify the output exactly

“Summarise this” gets you a summary of unknown length in an unknown shape. Say the shape: how many items, which fields, what order, how long, what to leave out.

Do: “A markdown table with columns Part, Finding, Severity (1–5), Action. One row per finding. No preamble.” Being this prescriptive feels rude and works extremely well.

3 · Show two or three examples

Few-shot prompting. One worked example conveys more about tone, granularity and format than a paragraph of description, because it is the format.

Do: include a real input and the exact output you would have written. Best technique for consistency across many runs, and the one people use least.

4 · Let it work before it answers

“Work through the calculation step by step before giving the answer” measurably improves multi-step reasoning, because each intermediate step becomes context for the next one (module 4.3).

Note for 2026: reasoning models do this internally, so the explicit instruction adds little with them and still helps with ordinary models. Ask for the working when you need to check it, which for anything numerical is always.

5 · Permit “I don't know”

Left to itself, the model produces the most plausible answer, and a plausible answer to an unanswerable question is an invention (module 4.3). Make the honest answer an explicitly available option.

Do: “If the documents do not contain the answer, reply exactly: NOT IN SOURCES. Do not use outside knowledge.” Cheapest hallucination reduction available.

6 · Split the task

A prompt asking for six things at once does all six adequately. Three prompts each asking for one thing do each one well, and you can inspect the intermediate results.

Do: extract, then analyse, then write. Section 12.4 has an exercise. This is also the difference between a fragile demo and a reliable process.

One more, for anything that matters

Ask for the sources and check them. “Quote the exact sentence you are relying on, with its clause number” turns a fluent claim into something verifiable in ten seconds. If it cannot produce the quotation, you have learned something important.

12.6 · What does not help

A lot of prompt folklore circulates. Some of it is real, some is cargo cult. Honest verdicts, with the reasoning.

How to tell folklore from technique

A real technique gives the model information or structure it did not have. Folklore tries to change its attitude. Context, examples, format specifications and decomposition are information. Flattery, threats, urgency and incantations are attitude — and while some of them produced measurable effects on older models, none of them is a reliable engineering practice. If you want to know whether something works for your task, you now know how to find out: the evaluation set from module 8.

12.7 · AI coding assistants

The most widely used AI tool in most engineering departments is not a chat window — it is the assistant inside the code editor. They range from autocomplete that finishes the line, through chat that writes a function, to agents that edit several files and run commands. Everything in 12.1 about context and format applies. What is different is that the output runs, and it ends up in places where nobody reads it twice.

Where they genuinely save time

  • Boilerplate — argument parsing, file I/O, plotting, config handling, the fortieth data class.
  • Tests — especially the tedious edge cases, once you have said what the function is supposed to do.
  • Mechanical refactors — renaming, splitting a long function, moving to a newer API, with the existing tests as the safety net.
  • Explaining unfamiliar code — a legacy script, a library you have never used, a language you read once a year.
  • Data-wrangling scripts — reshaping a test-rig export, merging two spreadsheets, a one-off conversion. Small, checkable, thrown away afterwards.

Where they are confidently wrong

  • Subtle domain logic — your sign conventions, your coordinate frames, the reason that offset is there. The assistant has never seen your system.
  • Numerics — units, filter edges, integer overflow, accumulated floating-point error, off-by-one windows. The code looks right and is wrong by a little.
  • Safety-relevant embedded code — timing, memory, concurrency, defensive checks, coding standards. Generated from public code, which is mostly not written to that bar.
  • Security — it reproduces the insecure patterns common in its training data, and it does so fluently.

How to work with one

  1. Small tasks. One function, one test file, one refactor at a time. A 400-line answer is a 400-line review.
  2. Give context and constraints. The interface it must fit, the language and library versions, a real sample of the input data, and what it must not do (12.1, “write code”).
  3. Ask for the tests first. Read them and check they encode what you mean, with a known value worked out by hand. A test written from the same misunderstanding as the code will pass.
  4. Read every line. Especially the lines that look like boilerplate — that is where the verify=False hides.
  5. Run it, on real input and on input you know the answer for. Code that has not run has not been reviewed.
The review obligation

Generated code is your code. Your name is on the commit, and “the assistant wrote it” is not a defence in a code review, an incident report or an audit. Review it as you would a capable new colleague's first pull request — with more care if anything, because it is fluent, consistently formatted and never hesitant, and none of those things correlates with being correct.

The time saved writing code is partly spent reading it. Measured results vary widely: large gains on small, well-defined tasks, and at least one controlled study in which experienced developers were slower on their own mature codebases while believing they were faster. Measure it on your own work before planning around it.

The risks that are specific to code

Secrets and proprietary code in the prompt

The assistant sends your open files — and an agent may send much of the repository — to wherever the model runs. Keys in a .env file, credentials in a test fixture and unreleased control code all travel with it. Module 10.5 is the rule for what may go where; exclusion lists in the tool settings are how it is enforced.

Licence contamination

A model can reproduce training code verbatim, including copyleft code, which then sits in a commercial product without its licence. Switch on the vendor's filter for verbatim matches, and run licence scanning in CI (module 10.7).

Hallucinated packages and typosquatting

Assistants invent plausible package names. Attackers register the names that models commonly invent, and the names one typo away from popular packages, and fill them with malware. One pip install of a suggested name is code execution on your machine (module 10.6, supply chain). Install only from your internal mirror, and check that a package exists, who publishes it and how long it has been around.

Insecure patterns

eval on input, SQL built by string concatenation, TLS verification switched off, hard-coded credentials, outdated cryptography, permissive file permissions. All common in public code, so all common in generated code. Static analysis and secret scanning in CI catch most of them; a reviewer who knows to look catches the rest.

Team policy: what to settle before people need it

  • Which tools are approved, on which tenant, with no-training terms — and which personal accounts and browser plug-ins are not. If there is no approved tool, people will use an unapproved one (module 10.5, shadow AI).
  • What code may be sent: by repository or classification, not by individual judgement. Typical exclusions are calibration data, unreleased control software, customer data and code received from third parties under NDA.
  • Agent permissions: whether an agent may run commands, install packages or push, and on which machines (module 9.5).
  • Safety-related software. Where code is developed under ISO 26262, the tools used to develop it fall under the standard's tool-confidence requirements (part 8), and the code must meet your coding guidelines — typically MISRA — with traceable review. An assistant is not allowed in that workflow until your functional-safety process says how it is qualified and reviewed. In many organisations today the answer is simply no.
  • CI controls: secret scanning, licence scanning, static analysis and a dependency allow-list. These catch what review misses, whoever wrote the code.
  • Disclosure: whether AI-assisted changes are marked in commits or pull requests. Cheap to decide early, and useful evidence later.

  • Run the review lab on the projector with the room calling out line numbers. Expect the unit conversion to go fast and the moving average to split the room — that is the point: the off-by-one in a filter window is exactly the defect that survives review because the code looks idiomatic.
  • On the power line in snippet 1, someone will flag 9549. Let them, then show the explanation. Flagging correct code costs review time too, which is the real trade-off: reviewing generated code well is a skill, and it takes the time it takes.
  • If anyone from embedded or functional safety is in the room, ask them what their process says about assistants today. Usually the honest answer is “nothing yet”, which is itself the action item.
  • Do not frame this as anti-assistant. The engineers who get the most from these tools are the ones who review hardest, give the most context, and keep the tasks small.

12.8 · Run the workshop

Five exercises, about fifty minutes. People work on their own laptops with whatever approved tool you have; the value is in comparing results out loud after each one.

How to run it so it lands

After each exercise, ask two people to read out their prompt — not their result. The room learns far more from hearing how differently two people framed the same request than from seeing a good output. And keep exercise 5 to the end: discovering that the model will confidently invent a clause number is the lesson people carry back to their desks.

  • This module is the easiest sell of the fifteen and the one people request. Use that: it is a good first session for a sceptical department, with module 1 and the RAG demo from module 4.8.
  • Do not let it become a tips-and-tricks session. Anchor every technique back to “narrowing the space of plausible continuations” from the top of this page, or in six months people will be repeating incantations they do not understand.
  • Have a strong opinion ready on the myths section. People have read a great deal of nonsense and will be relieved to be told which parts they can stop doing.
  • Collect the prompts people write. They are the beginning of your organisation's prompt library and, more usefully, of the evaluation set from module 8.

Where we go next
