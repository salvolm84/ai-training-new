Module 19 · Part IV — Shipping it

Deploying and running models

The notebook ends with a number on a test set. The product starts there. Getting a model onto an ECU, a bench PC or a server, proving which version made which decision, releasing it without hurting anyone, and noticing when it quietly stops working — that is most of the job, and it is what this module is about.

The sentence to take away

A deployed model is a software component with a data dependency. It needs everything any production component needs — version control, a release process, monitoring, an owner and a tested way back — plus one thing ordinary software does not: a continuous check that the world still looks like the data it learned from.

19.1 · The model is the small box

In 2015 a group of Google engineers published a paper called Hidden Technical Debt in Machine Learning Systems. Its best-known contribution is a single picture: a production ML system drawn as a set of boxes, with the actual machine-learning code as a tiny square in the middle. Every other box is ordinary engineering — and every other box is somewhere the system can break without the model changing at all.

What surrounds a production model

Click a box

Authored diagram, after Sculley et al., NeurIPS 2015. The box list is theirs; the relative sizes are illustrative, not measured. The point survives any reasonable re-drawing: the part your data scientist wrote is the smallest part.

Training/serving skew

The feature code is written twice — once in Python for training, once in C for the ECU — and the two disagree in some corner (a filter's initial state, a rounding mode, a unit). The model is fine; its inputs are not the inputs it was trained on. Share the code, or test the two implementations against each other on recorded data.

Undeclared consumers

Somebody downstream starts using your model's score for a purpose you never validated — a dashboard, a second threshold, a warranty report. Now your next release breaks their system. Know who reads your outputs.

Entanglement

Change one input's scaling and every learned weight is now slightly wrong. In ML, nothing is truly modular: changing anything changes everything, which is why the rest of this module insists on versioning and re-validation.

  • About 4 minutes. Click through three or four boxes; let the audience suggest which box has bitten their own projects. Configuration and feature extraction are the usual answers.
  • Expected question: “Is this still true with modern tooling?” Yes. The tooling has got better at each box; it has not removed any of them.
  • For people coming from embedded software: none of this is new to you. The new part is the data dependency, and that is what sections 19.2 and 19.6 deal with.

19.2 · Version everything, or you cannot answer the question

Sooner or later someone will ask: why did the system make that decision, on that day? An auditor, a customer-quality engineer, a court. To answer, you need to rebuild the exact model that was running. A model is the product of five things, and losing any one of them means you cannot.

WhatWhy it mattersHow it is usually pinned
DataTables grow, labels get corrected, a filter changes which rows are included.Immutable snapshot with an ID or content hash; never “the table as it is today”.

The output — the trained weights — goes into a model registry with a version number and a record of all five inputs. That record is the model's birth certificate.

Two things the lab shows

A fixed seed is not reproducibility. Unpin the data alone and the model changes, however carefully the seed was set. And bit-identical is not always necessary: unpin only the environment and the weights differ in the seventh decimal place while every decision stays the same. Decide in advance which one your use case needs — a safety argument usually needs the first; a planning tool can live with the second.

  • About 6 minutes. Start with everything ticked (bit-identical), then untick “seed” and press rebuild twice — the boundary moves each time. Then tick seed again and untick data.
  • On GPUs, even a fixed seed and fixed data can give different results run to run, because some parallel operations add numbers in a non-deterministic order. Most frameworks have a “deterministic” mode; it is slower, and for certification-relevant models it is worth it.
  • Expected question: “Do we really need to keep every dataset?” You need to keep every dataset that trained a model which is, or was, in a product. Storage is cheap compared with being unable to answer the question.

19.3 · Where it runs: serving patterns and the latency budget

“Deployment” means very different things depending on when the answer is needed and where the data is. Four patterns cover almost everything.

Batch

Run over yesterday's data on a schedule; write results to a table. Example: scoring every warranty claim overnight for likely fraud, ranking tomorrow's bench test plan. Latency: hours, and nobody minds. Easiest to run, easiest to roll back.

Online (request–response)

A service answers one request at a time. Example: the inspection station sends an image, gets accept/reject back. Latency: tens to hundreds of milliseconds. Now you own availability, timeouts and a fallback for when the service is down.

Streaming

The model consumes a continuous feed and emits results as data arrives. Example: anomaly detection on test-bench channels at 1 kHz, plant-wide sensor streams. Latency: milliseconds to seconds; state and ordering become your problem.

On-device / edge

The model runs where the data is: an ECU, a camera, a bench PC. Example: an on-vehicle classifier in a 10 ms control cycle. No network, hard deadlines, fixed memory, and updating it means a software release — over the air or in the workshop.

TargetCompute and memoryTimingUpdating it
On-vehicle ECUFixed and small: kilobytes to a few megabytes for the model, shared CPU or a small accelerator.Hard real-time; a missed deadline is a fault.Full software release, homologation impact, OTA or workshop.

For anything in a control loop, the question is not “how fast is the model?” but “does the whole chain, sensor to actuator, finish before the deadline — every time?” The model is one stage of several, and averages hide the cycles that matter.

Sampling is not a timing guarantee

Twenty thousand cycles without a miss tells you the miss rate is probably below about 1 in 6,700 (the “rule of three”: 3 ÷ N). At 100 Hz that could still be one miss a minute. For a function with a safety or homologation case, timing is argued with worst-case execution time analysis and a scheduler designed for it — which is far easier for a fixed-size neural network with no data-dependent loops than for most code, and is one of the quiet advantages of putting a small model on an ECU. Module 20 picks this up.

  • About 7 minutes. Start on ECU: it meets 10 ms comfortably. Switch to Cloud: the median alone is over the deadline. That single click ends most “let's run it in the cloud” conversations for control functions.
  • Then the bench PC: the median is fine, the tail is not. Push the stall chance up and watch misses per hour climb while the median barely moves. That is the general-purpose-OS problem in one slider.
  • Expected question: “Can't we just make the model faster?” Drag inference time down on the cloud target. The network round trip does not care how fast your model is.

19.4 · Making it fit: quantisation and pruning

A trained network stores each weight as a 32-bit floating-point number. An ECU may have a few hundred kilobytes for every ML function in the car, and integer arithmetic is far cheaper in silicon and energy than floating point. Two standard techniques shrink a model after training:

  • Quantisation — store each weight as a small integer plus a shared scale factor. 8 bits makes the model four times smaller; 4 bits, eight times. The question is how much accuracy it costs.
  • Pruning — set the smallest weights to exactly zero. Saves memory only if the model is stored in a sparse format, and saves time only if the hardware has kernels that skip zeros.
scale = max|w| ÷ (2bits−1 − 1)    q = round(w ÷ scale)    w′ = q × scale Symmetric uniform quantisation. “Per tensor” uses one scale for a whole layer; “per channel” gives each neuron's weights their own scale, which costs a few extra numbers and protects neurons with small weights.

A quantised model is a different model

Report two numbers, not one: accuracy, and agreement with the float model you validated. Two models can both be 96% accurate and disagree on 3% of cases — and those cases are exactly where nobody has looked. Whatever runs on the target is the thing you validate, test and sign off; the float model on the data scientist's laptop is a development artefact.

  • About 8 minutes. Walk 8 → 4 → 3 → 2 bits per tensor; at 8 bits nothing changes, at 2 bits the boundary falls apart. Switch to per channel at 3 bits to show the cheap fix.   • Expected question: “Why not always use 4 bits?” Because the target needs kernels for it, the accuracy loss must be re-validated on every release, and below 8 bits the tooling and the certification evidence are both thinner.

19.5 · Releasing it: shadow, canary, A/B and rollback

Every new model version is a hypothesis that it is better than the old one. Offline evaluation (module 8) is the first test; the release strategy is the second, run on real traffic. The strategies differ in two things: how many decisions the new model makes before you know, and how quickly the evidence accumulates.

Big bang

Replace the old model everywhere at once. You compare the new model against last month's numbers — which were measured under last month's conditions. Fast, and every decision is exposed.

Canary

Send a small share of traffic (one line, one plant, 1% of the fleet) to the new model; widen in stages if nothing goes wrong. The old model keeps running alongside as a concurrent control.

A/B test

Split traffic evenly for a fixed period and compare. Statistically clean, and half of your decisions are made by the unproven model.

Shadow mode

The new model sees every input and its output is logged, but the old model still makes every decision. No exposure at all, and both models are judged on the same parts. Costs double the compute, and it cannot show effects that depend on acting differently.

Tests used: big bang compares v3.2's audited error rate with the historical 3.0% (one-sample z); canary and A/B compare v3.2 with v3.1 on concurrent traffic (two-proportion z); shadow compares both models on the same audited parts (McNemar's test on the parts where they disagree), and keeps v3.1 running in shadow after promotion. Tests are repeated hourly on cumulative data, which is why the threshold must be well above 2. “Extra wrong decisions” is the expected number caused by v3.2 compared with v3.1 on the same parts.

A canary without statistical power is a ritual

Run the lab with a small degradation: at 5% of traffic, with errors at 3% and a tenth of parts audited, the canary simply does not see enough wrong decisions to notice — and then it promotes itself. Before choosing a canary share and duration, work out how many labelled examples it takes to detect the smallest degradation you care about. That arithmetic, not habit, sets the plan.

Rollback is a capability, not a button

Rolling back a cloud service takes seconds. Rolling back an ECU model means an OTA campaign or a workshop visit, and the vehicles keep driving in the meantime. That asymmetry is why shadow mode on the vehicle — the new model runs, logs, and decides nothing — is so valuable in automotive: you collect the evidence before you have anything to roll back.

  • About 8 minutes. Show one fortnight first, then press “Run 200 rollouts”. Typical reading at the defaults: shadow catches it with zero exposure; big bang catches it fast but after hundreds of bad decisions; the canary usually gathers enough evidence only after it has already promoted itself; A/B is slow and exposes half the line.
  • Then set the degradation to 0 and run 200 again: the false-alarm column. Big bang raises false alarms because it compares against a historical baseline in a process that varies day to day. Concurrent comparison cancels that out — which is the real argument for canaries and shadows.
  • Expected question: “Why not just wait for more data?” You can — raise the threshold and watch detection slow down and exposure rise. There is no free setting; you are choosing a trade-off and should write down which.

19.6 · Running it: the production monitoring dashboard

Module 7.5 introduced drift. In production you need it as a set of dashboards with agreed alert levels and a named person who receives them. There are four layers, from cheapest and fastest to most expensive and slowest:

  1. Data quality — missing values, stuck sensors, values out of range, unit changes. Free, immediate, and catches the most embarrassing failures.
  2. Input drift — has the distribution of each input moved away from the training data? Needs no labels.
  3. Prediction drift — is the model flagging more or less than it used to? Needs no labels either.
  4. Performance against ground truth — the only layer that tells you whether the model is actually right. Arrives late and only for a sample.
PSI = Σbins (q − p) · ln(q ÷ p)     KS = maxx |Ftoday(x) − Ftrain(x)| PSI (population stability index) compares the share of today's data, q, with the share of the training data, p, in each of ten bins set by the training data's deciles. Below 0.1 is usually read as stable, above 0.25 as a significant shift. KS (Kolmogorov–Smirnov) is the largest gap between the two cumulative distributions; with large daily samples it flags even trivial shifts, which is why PSI is more often used for alerts.

Drift is not failure

In the seasonal scenario the temperature input drifts far past any PSI alert level, and the model stays right, because the relationship it learned still holds. An alert on drift is a reason to look, not a reason to retrain.

Failure is not always drift

In the concept-change scenario the inputs do not move at all. A new bearing supplier wears out at lower vibration levels, and only the late, sampled ground truth can see it. If you have no ground-truth pipeline, you will find out from warranty claims.

Do not retrain on broken data

When a feature is stuck or missing, the right action is the kill switch and a fix to the pipeline. Retraining teaches the model that the broken feature is normal — and then the fix breaks the model.

  • About 9 minutes; this is the centrepiece. For each scenario, drag “today” from day 30 forward slowly and ask the room, at each alert, “what would you do now?” before revealing the verdict.
  • Sensor change: input and prediction drift fire within a day, labels confirm three weeks later. The question to ask is “who knew the sensor had changed?” — usually purchasing did, and nobody told the model owner.
  • Concept change: nothing fires until the labels arrive. Set the delay to 40 days to make the point painful. Then retrain and walk forward.
  • Under no drift, PSI with 300 events a day and ten bins sits around 0.03 from sampling noise alone. That is why alert levels below about 0.1 produce a stream of false alarms.

The two that matter most

A kill switch with a defined fallback, and a log that ties every decision to a model version. The first limits how bad your worst day can be. The second means that when someone asks what happened, you can answer with evidence rather than reconstruction. Both are cheap to build at the start and very expensive to add after an incident.

  • About 3 minutes. Hand it out with the module 7.8 and 9.8 checklists; together they cover data, agents and operations.
  • The item most often missing is the tested rollback. Ask when anyone last actually did one.
  • “Fallback” must be a behaviour, not a sentence: what does the vehicle, the station or the bench do in the second after the model is switched off?
