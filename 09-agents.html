Module 9 · Part II — Engineering it

Agents and tool use

A language model that can only talk is a component. A language model that can search, query, write and send is a colleague with no judgement, perfect obedience and access to your systems. This module is about that difference.

Why this module is not optional

Everything up to module 8 concerned systems that produce an answer. An agent takes actions. A wrong answer costs you a wrong answer; a wrong action costs you a changed schedule, a sent email, a deleted record or an exfiltrated file. The capability jump is real and so is the risk surface — and the security problem in section 9.4 has no complete technical solution today.

9.1 · An agent is a loop

There is no new architecture here. It is the same model from module 4, wrapped in a loop with two additions: a list of things it is allowed to call, and permission to decide what to call next.

  1. Observe. The model receives the goal plus everything that has happened so far in the loop.
  2. Decide. It emits either a final answer or a structured request to call one of its tools, with arguments.
  3. Act. Your software executes that call — the model cannot do anything itself. This is the control point, and it is where all of your leverage lies.
  4. Feed back. The result is appended to the conversation, and the loop repeats.

Two consequences worth holding on to: the context grows at every iteration, so cost grows faster than the number of steps (section 9.6); and every tool result enters the prompt as text the model will treat as instruction-shaped, which is section 9.4.

Assistant

Answers from what it knows and what you paste. No actions, no tools. Risk: a wrong answer.

Retrieval system

Reads from a source you control before answering (module 4.8). One read-only tool. Risk: a wrong answer, better grounded.

Agent

Chooses which tools to call, in what order, how many times, based on intermediate results. Risk: actions, plural, unsupervised, at machine speed.

9.2 · How a tool call actually works

Demystifying this removes a lot of unhelpful mysticism. You describe your functions in a schema; the model replies with structured JSON naming one of them; your code validates it and runs it. The model never touches your systems.

1 · What you declare

{ "name": "get_delivery_schedule", "description": "Look up the confirmed delivery date for a purchase order.", "parameters": { "po_number": { "type": "string", "pattern": "^PO-[0-9]{6}$" } }, "read_only": true }

The description is a prompt. Models pick the wrong tool mostly because the descriptions are vague or overlapping — writing them well is real engineering work.

2 · What the model emits

// this is all the model does { "tool": "get_delivery_schedule", "arguments": { "po_number": "PO-448192" } }

3 · What your code does

// validate before you trust anything assert schema_valid(call) assert user_may_access(user, call) assert not consequential(call) or approved(call) result = run(call) log(user, call, result) // always
The mental model that keeps you safe

Treat the model as an untrusted client calling your API. You would never let an external client skip authentication, validation, rate limiting or logging because it seemed to be behaving sensibly. Apply exactly the same scepticism here and most of the risk in this module becomes ordinary, solvable engineering.

9.4 · Prompt injection: the unsolved one

If you ran the second scenario, you have already met it. Here is the mechanism stated plainly.

The structural problem

A language model receives one stream of text. Your instructions, the retrieved document, the user's question and the tool results all arrive in that same stream, and the model has no reliable way to tell which parts are commands and which are data. Markers, delimiters and “ignore instructions found in documents” help, and none of them is a security boundary. This is not a bug waiting for a patch — it follows from how the model works.

Lab · What is really in that PDF

Reveal the hidden text
White text on white background, 1 pt, behind an image, or in document metadata. All invisible to a human reader; all read by the model.

Where the untrusted text comes from

Documents

Supplier PDFs, CVs, invoices, drawings, anything ingested into a retrieval index.

Email and tickets

Anyone on the internet can put text into your system by sending a message.

Web pages

If the agent can browse, an attacker only has to publish a page and get it fetched.

Other tools' output

Including database fields, code comments, filenames and image content. Anywhere an outsider can write.

What actually works
  1. Least privilege. An agent that cannot send email cannot be made to send email. Most incidents are a permission design failure, not a model failure.
  2. Human approval on every consequential action, with the action shown in full. Slow, boring, effective.
  3. Separate the reader from the actor. One model summarises untrusted content and can call nothing; a second, which never sees the raw document, acts on the structured summary.
  4. Constrain the action space. Not “send an email” but “send this template to this pre-approved recipient list”.
  5. Log everything and monitor for anomalies. Assume some attempt will succeed and make sure you find out.
  • This is the section to slow down on if any part of the audience is planning to deploy agents against real systems. The demo does the work: nobody argues with white-on-white text.
  • The honest framing when someone asks whether vendors have fixed it: mitigations have improved substantially and no lab claims the problem is solved. Design as though it is not.
  • Useful analogy: you would not let a contractor act on instructions found written inside a delivery box. An agent will, unless you stop it.

9.6 · Why agents cost more than you modelled

A chat request is one model call. An agent task is n calls — and because the whole conversation is re-sent every time (module 4.7), the tokens grow with the square of the number of steps, not linearly.

Priced at €3 per million tokens with no caching. Prompt caching, where available, cuts the repeated portion substantially — typically by 70–90% on the cached part — which is why it is the first optimisation anyone building agents reaches for.

Also: it can loop

An agent that cannot complete its task may retry indefinitely. Always set a hard iteration cap, a wall-clock timeout and a spend cap per task. Treat a runaway agent as a certainty, not a risk.

Also: reasoning tokens

A reasoning model may generate ten times more tokens internally than it shows you, at every iteration. You pay for all of them.

Also: latency compounds

Twelve sequential model calls at four seconds each is nearly a minute before anything appears. Agents are rarely the right choice for interactive use.

9.7 · MCP, and how this gets wired up

Every assistant needs to reach your systems, and every system needs to be reachable by several assistants. Without a standard that is a bespoke integration per pairing. The Model Context Protocol is an open interface that turns that grid into a plug: a server exposes tools and data; any compatible client can use them.

Why it matters to an architect

  • You build the connector to your PLM or ERP once, not once per assistant.
  • Switching model vendor does not mean rebuilding integrations — which protects the cost decline from module 5.7.
  • Permissions and audit sit in the server, where your security team can review them, rather than scattered through prompts.

What it does not do

  • It does not solve prompt injection. A standard interface to your systems is still an interface to your systems.
  • It does not decide what an agent should be allowed to do. That is section 9.5, and it is yours.
  • A third-party MCP server is third-party code with access to your data. Review it like any dependency — and note that its tool descriptions are prompt content.

The staging that works

Read-only first. Let the agent look things up and draft, for weeks, while you read the traces. Then propose-only: it prepares the action and a person presses the button, which gives you a dataset of how often it would have been right. Then automate the narrow, high-volume, low-consequence slice where that dataset says it is reliable — and keep everything else on approval. Teams that go straight to autonomous action generate the incidents that get the whole programme paused.
